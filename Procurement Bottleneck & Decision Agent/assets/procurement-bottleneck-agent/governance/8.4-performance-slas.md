# Performance SLAs — L0-8.4 (UI) / L0-8.5 (Orchestration) / L0-8.6 (Tool calls)

**Agent:** `procurement-bottleneck-agent`
**Status:** SLA targets defined — **p50/p95/p99 validation on live under peak load pending**

## 1. Trigger types (L0-8.1) and budgets
| Trigger | Mode | Timeout budget |
|---|---|---|
| User-initiated (Fiori/Joule query) | synchronous | target response below the UI SLA (§2) |
| Event-driven (`po.confirmation.overdue`) | async | best-effort, bounded by tool timeouts |
| Scheduled (14-day due-date sweep) | periodic | batch; no UI SLA |

## 2. UI layer SLA (8.4) — targets to validate on live
| Metric | Target |
|---|---|
| Time-to-first-token (verdict) | p50 ≤ 3s · p95 ≤ 8s · p99 ≤ 15s |
| Time-to-complete-report | p50 ≤ 6s · p95 ≤ 15s · p99 ≤ 25s |

Targets are customer-visible commitments; validate end-to-end (not only API level) under expected peak. Feeds the ESCE support concept (L0-1.5).

## 3. Orchestration / reasoning (8.5)
- **Bounded by design:** exactly 2 LLM hops; deterministic core in between. No free ReAct loop.
- Token ceiling 52,000/run (`config.TOKEN_BUDGET_PER_RUN`) prevents runaway reasoning cost (ties to Cost Per Transaction Baseline, L0-4.6).

## 4. Backend / tool-call performance (8.6)
- Per-tool timeout `config.TOOL_TIMEOUT_SECONDS = 30`.
- Tested fallback + circuit breaker after `CIRCUIT_BREAKER_THRESHOLD = 3` consecutive failures (`app/resilience.py`, `tests/test_resilience.py`).
- Per-tool latency is logged by observability (L0-6.7: `latency_ms`, `tool_name`) and surfaces on the operational dashboard post go-live.
